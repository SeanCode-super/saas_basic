# Flowable 8 开发库恢复演练

适用于天枢 MySQL 开发库曾由 Flowable 8.0.0 升级、后来又被 7.0.1 打开，导致物理结构与引擎元数据不一致的情况。工具从当次完整备份构造一份可独立导入的数据库。历史上通过验收的 Flowable 8 备份用来核对官方建表结果和识别后续新增的流程定义。

## 运行

需要 Python 3.11 及以上、项目 JDK、可执行的 `mysql`、`mysqld`、`mysqldump`，以及包含 `flowable-engine-8.0.0.jar` 的已打包 Spring Boot 应用。MySQL 工具使用与源库相同的版本、平台和标识符大小写设置。输入是可信的单库完整 mysqldump，包含表结构、数据、触发器、例程和事件。开发机本次源备份包含两个触发器。输出路径使用一个尚未创建的目录。

```sh
python3 bin/workflow-recovery/rehearse.py \
  --current-dump /path/to/frozen-current.sql \
  --verified-v8-dump /path/to/trusted-flowable8.sql \
  --app-jar /path/to/saas-basics-app-0.1.0-SNAPSHOT.jar \
  --java /path/to/jdk/bin/java \
  --output-dir /path/to/new-recovery-directory
```

工具启动一个只绑定本机的新 MySQL 进程。所有输入文件都在私有实例中恢复，命令结束时关闭实例并清理临时目录。每轮演练的产物独立保留。再次运行使用新的输出目录。

## 恢复与核验

1. 使用应用实际附带的 Flowable 8 引擎初始化空库，检查其表、列、索引和约束与已验证的 8 版备份相同。面对意料之外的表结构或版本组合，会停止并报告差异。
2. 导入本次备份中的平台业务对象和全部当前业务记录，包括流程 XML、部署、运行实例、历史记录、待办和业务侧流程映射。引擎配置和 ID 分配器也来自本次备份。
3. 新实例保留引擎在空库生成的版本元数据和 `create(8.0.0.0)` 初始化历史。两个旧 Liquibase 跟踪表以及源库原始版本历史保存在输入备份。报告同时记录三个库的版本值，以及两张旧表的记录数和摘要。
4. 对每张业务表和引擎表按列名计算逐行摘要，再核对整表摘要及行数。引擎的两张属性表仅排除官方重建的版本元数据。重新扫描每个外键的孤儿记录，核对平台软关联、数据库对象定义、AUTO_INCREMENT 计数器和新增定义 ID。
5. 导出全库，重新导入独立 schema 并重复结构与数据校验。从这次重导的库启动真实 Flowable 8，关闭 schema 自动更新和异步作业执行，逐个解析已部署的 BPMN，并查询定义、待办、运行实例和历史实例。全部检查通过后才发布 `recovered.sql`。

成功输出包含可独立导入的 `recovered.sql`、两个引擎启动日志，以及含输入/输出 SHA-256、每表行数和摘要的 `validation.json`。目录权限为当前用户专用。日志和备份应与开发库备份按相同权限管理。

## 本地切换和撤回

停写范围包括两个后端入口、后台任务、工作流执行器和任何直接写库客户端。停止后生成当前全库的一致备份，将该备份重新交给上述命令。确认报告中的业务联接、流程定义和在途任务与停写时一致。

完整平行库可以切换数据源。先保留原库与两个入口原有的连接配置，在目标库启动对应版本的服务，验证 Flyway、引擎、平台健康和业务查询。开放写入前可将两端切回原来的数据源，并使用与原库配套的应用版本。若使用同一 MySQL 实例单条 RENAME TABLE 交换整组引擎表，须在停写窗口内验证来源和目标的全部表名、跨组外键、触发器、唯一约束名称，以及反向交换的结果；任何新业务写入都会改变回退基准。

开放写入后若需撤回，应先冻结写入并保留新库，在新库写入与旧库之间完成事务对账和回放后再切换。直接切回最初快照会丢失窗口后的新数据。
