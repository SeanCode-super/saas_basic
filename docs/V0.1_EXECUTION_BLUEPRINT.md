# SaaS Basics v0.1 执行蓝图

状态：`Accepted`

版本：`0.1`

更新日期：`2026-08-09`

本文档是当前项目的唯一执行基线。其它架构文档保留为历史设计输入；当内容冲突时，以本文档为准。

## 1. 产品定位

SaaS Basics 不是某个行业的 SaaS 产品，也不是后台管理模板。它是一套：

> 开源、AI 原生、面向多行业的企业应用开发底座。

底座负责解决所有企业应用都会重复建设的能力：

- 多租户和平台运营
- 企业集团、法人公司、组织和人员任职
- 账号、身份、角色、菜单、API 和数据权限
- 应用、门户、功能开关、配置和审计
- 模块脚手架、元数据、数据库迁移和代码生成
- 模型接入、知识库、Agent、工具、AI 工作流和治理

CRM、ERP、WMS、制造、医疗、教育、政务等行业能力以独立模块或行业包的形式构建在底座之上。

## 2. v0.1 成功标准

v0.1 的目标不是覆盖所有平台功能，而是证明底座可以安全、稳定地承载第三方业务模块。

发布必须同时满足：

1. 一个租户可以建立集团、多级法人公司和组织体系。
2. 一个人可以在多个公司、部门和岗位任职，并获得不同权限。
3. 用户只能访问当前授权租户和组织范围内的数据。
4. 菜单、按钮、API、数据权限使用同一套权限语义。
5. 第三方开发者可以通过模块模板增加一个真实业务模块。
6. AI 可以在权限约束下查询知识和调用业务工具，并完整留痕。
7. 新环境可以通过文档和容器化依赖完成一键启动与测试。

## 5. 企业核心领域模型

### 5.1 核心概念

| 概念 | 含义 | 关键约束 |
|---|---|---|
| Platform | 底座运营方 | 可以管理租户，但跨租户操作必须显式授权和审计 |
| Tenant | 数据与安全隔离边界 | 不等于公司，也不等于组织树 |
| Enterprise Group | 企业集团或股份公司 | 一个租户可以包含多个集团 |
| Legal Entity | 法人公司或独立核算主体 | 具有统一社会信用代码等法定属性 |
| Business Unit | 事业部、区域或业务单元 | 可以跨法人组织业务 |
| Org Unit | 部门、中心、团队或分支机构 | 具有主组织树，同时允许辅助关系 |
| Person | 自然人 | 与登录账号和员工关系分离 |
| Employment | 人与法人公司的劳动或合作关系 | 区分员工、外包、顾问、合作伙伴 |
| Assignment | 人员任职 | 关联公司、组织、岗位、有效期和主次任职 |
| Position | 岗位编制或职责位置 | 不等同于角色 |
| User | 系统账号 | 可以绑定一个人和多个登录身份 |
| Identity | 密码、手机号、邮箱、OIDC 等登录身份 | 同一用户可以有多个身份 |
| Role Binding | 角色授予关系 | 授予范围可以是租户、公司、组织或任职 |
| Application | 安装在租户内的应用 | 决定菜单、权限、功能和 AI 工具边界 |

### 5.2 关系模型

```text
Platform
  -> Tenant
      -> Enterprise Group
          -> Legal Entity
              -> Org Unit
                  -> Position

Person
  -> Employment -> Legal Entity
  -> Assignment -> Org Unit + Position
  -> User -> Identity

User / Assignment / Org Unit
  -> Role Binding -> Role -> Permission
```

组织不能只用一棵 `department` 树表达。v0.1 采用：

- 一棵主组织树，用于默认管理归属和数据范围。
- 可选辅助关系，用于虚拟团队、矩阵组织和项目关系。
- 事业部和区域默认建模为带类型的 OrgUnit，需要跨法人时通过辅助关系表达。
- 任职记录表达人员在不同公司、部门和岗位中的有效关系。
- 权限绑定引用任职和组织范围，避免把组织语义复制到角色表。

### 5.3 建议模块归属

| 模块 | 拥有的核心对象 |
|---|---|
| tenant | Tenant、套餐最小模型、租户生命周期 |
| organization | EnterpriseGroup、LegalEntity、OrgUnit、Position、Person、Employment、Assignment |
| iam | User、Identity、Credential、Session、Role、Permission、RoleBinding、DataPolicy |
| application | Application、Portal、Terminal、Menu、FeatureFlag |
| system | Dict、Config、Sequence、I18n |
| audit | LoginLog、OperationLog、SecurityEvent、AI Audit |
| ai | Provider、Model、Prompt、KnowledgeBase、Agent、Tool、Run、Usage |
| devkit | ModuleDefinition、Metadata、Template、GenerationRun |

### 5.4 数据库硬约束

- 所有租户数据表必须有不可为空的 `tenant_id`。
- `tenant_id = 0` 仅允许用于经过评审的平台公共表。
- 普通请求的 `tenant_id` 来自认证上下文，不接受请求体指定。
- 所有唯一索引默认包含 `tenant_id`。
- 所有高频查询索引以 `tenant_id` 作为前导列之一。
- 跨租户查询必须使用独立服务入口、独立权限码和审计事件。
- 表只允许所属模块写入；跨模块读取通过公开 Facade、事件或专用只读投影。
- 已发布迁移不可修改，只通过新版本迁移演进。

## 6. 权限模型

### 6.1 权限层次

1. 身份认证：用户是谁、当前使用哪个身份。
2. 租户访问：用户是否属于当前租户。
3. 应用访问：租户和用户是否开通当前应用。
4. 功能权限：菜单、页面、按钮和 API 是否允许。
5. 数据权限：允许访问哪些公司、组织、人员和业务对象。
6. 字段权限：敏感字段是否允许读取、编辑或导出。
7. AI 权限：允许使用哪些模型、知识库、Agent 和工具。

### 6.2 强制规则

- 后端是权限真相源，前端权限只用于交互呈现。
- 菜单可见不代表 API 可调用。
- 角色本身不保存用户数据，授权使用 RoleBinding 表达。
- 数据权限最终必须作用于查询或仓储层，不能只依赖 Controller 注解。
- 平台管理员不默认拥有租户业务数据访问权。
- 导出、敏感字段、跨租户和 AI 工具写操作必须单独授权。

## 7. AI 原生架构

### 7.1 AI 不是附加聊天框

AI 同时服务两类使用者：

- 开发者：生成模块、模型、迁移、接口、页面、测试和文档。
- 业务用户：检索企业知识、分析业务数据、触发受控业务操作。

### 7.2 AI 运行链路

```text
User Request
  -> Auth and Tenant Context
  -> AI Policy Check
  -> Model Router
  -> Prompt / Knowledge / Tool Planning
  -> Tool Permission Check
  -> Human Approval when required
  -> Tool Execution
  -> Result and Citation
  -> Audit / Usage / Evaluation
```

### 7.3 AI 模块边界

| 子域 | v0.1 能力 |
|---|---|
| Gateway | 统一请求协议、供应商适配、超时、重试、路由和降级 |
| Model Registry | 供应商、模型、能力、上下文长度、价格和状态 |
| Credential | 租户隔离、加密存储、轮换接口和脱敏展示 |
| Prompt | 模板、变量、版本、发布和回滚 |
| Knowledge | 知识库、文档、切片、向量索引、引用和权限过滤 |
| Agent | Agent 定义、模型策略、系统提示和可用工具 |
| Tool | 工具注册、MCP、输入输出 Schema、权限码和风险等级 |
| Vector Store | 统一 SPI、租户命名空间、权限元数据和一个默认适配器 |
| Runtime | Run、Step、ToolCall、状态机、重试和人工确认 |
| Governance | 配额、费用、审计、敏感信息、安全策略和评测 |

### 7.4 AI 不可违反的约束

- 每次 AI 运行必须绑定 `tenantId`、`userId`、应用和权限快照。
- RAG 检索必须先做权限过滤，不能检索后再隐藏结果。
- AI 工具调用使用与普通 API 相同的授权和数据权限。
- 高风险写操作默认需要人工确认，并支持幂等与回滚策略。
- Prompt、模型、知识版本和工具参数必须进入审计记录。
- 模型供应商不得看到未授权租户数据。
- AI 生成的代码只有通过编译、测试和安全检查后才能进入工作区。
- 模型供应商和向量数据库通过 SPI 接入，领域代码不依赖厂商 SDK。

## 8. 目标技术架构

### 8.1 架构形态

v0.1 采用模块化单体：

- 一个部署单元。
- 一个 MySQL 数据库。
- 模块拥有各自的数据表和公开契约。
- 模块间使用 Facade、领域事件或只读投影协作。
- 暂不引入微服务、分布式事务和动态插件运行时。

### 8.2 目标模块

```text
saas-basics-app
saas-basics-kernel
saas-basics-infrastructure
saas-basics-module-tenant
saas-basics-module-organization
saas-basics-module-iam
saas-basics-module-application
saas-basics-module-system
saas-basics-module-audit
saas-basics-module-ai
saas-basics-module-devkit
saas-basics-module-file          # v0.1 最小实现
saas-basics-module-scheduler     # v0.1 最小实现
saas-basics-module-integration   # v0.1 最小实现
```

### 8.3 模块内部结构

```text
module-x/
  api/              # 其它模块允许依赖的 Facade、DTO 和事件
  application/      # 用例编排、事务边界和权限入口
  domain/           # 领域对象、规则和仓储接口
  infrastructure/   # Mapper、外部适配器和仓储实现
  web/              # Controller 和请求响应转换
```

简单 CRUD 可以合并 application 和 domain，但跨模块依赖规则不可放宽。

### 8.4 依赖规则

- `app` 负责装配所有模块。
- 业务模块只能依赖 `kernel` 和其它模块的 `api` 包。
- `kernel` 不依赖 Spring MVC、MyBatis 或具体模型供应商。
- 模块不能 import 其它模块的 entity、mapper、service 实现。
- Dashboard 使用只读投影，不直接组合其它模块 Mapper。
- Audit 订阅领域事件，不要求每个模块依赖 Audit 实现。
- 使用 Spring Modulith 和 ArchUnit 在 CI 中执行边界检查。

## 11. 迁移顺序

1. 冻结新增功能和 V1-V24 迁移。
2. 建立根仓库、统一构建、CI、Testcontainers 和质量门禁。
3. 定义 `TenantAccessContext`，实现持久层强制租户隔离。
4. 接入 Spring Security，完成密码升级和会话迁移。
5. 新增 organization 模块和 V25+ 企业模型迁移。
6. 迁移现有部门、岗位、员工数据到新模型。
7. 重构 RoleBinding 和数据权限，使其引用公司、组织和任职。
8. 建立 application 模块，统一应用、门户、菜单和功能开关。
9. 新增 AI 模块，先完成 Gateway、模型、Prompt、Tool 和 Run。
10. 完成知识库、受控工具调用和一个开发助手示例。
11. 用一个真实业务模块验证 SDK、权限、迁移、AI 和前端生成链路。
12. 清理旧接口和页面，发布迁移说明和 v0.1。

## 12. 里程碑与 Token 预算

Token 是规划上限，不是功能完成度指标。每个里程碑独立验收，未通过不得进入下一阶段。

| 里程碑 | 主要交付 | Token 预算 | 预计周期 |
|---|---|---:|---:|
| M0 架构基线 | 本文档、仓库治理、CI、测试基线、模块规则 | 30万～50万 | 1～2 周 |
| M1 企业核心 | 租户、集团、法人、组织、人员、任职 | 100万～150万 | 3～5 周 |
| M2 IAM 与安全 | Spring Security、角色绑定、权限、审计、租户隔离 | 100万～150万 | 3～5 周 |
| M3 AI 核心 | Gateway、模型、Prompt、Tool、Run、知识库最小闭环 | 120万～200万 | 4～6 周 |
| M4 开发者平台 | 模块 SDK、迁移模板、代码生成、示例业务模块 | 100万～180万 | 4～6 周 |
| M5 发布加固 | 测试、性能、安全、文档、容器、升级指南 | 100万～170万 | 3～5 周 |

v0.1 总预算：`550万～900万 Token`。建议为返工、评审和兼容性预留至 `1000万 Token`。

## 13. 里程碑验收

### M0

- 后端和前端 clean build 可重复通过。
- ESLint、Stylelint 和测试命令无配置级错误。
- 本地依赖可以一键启动。
- Testcontainers 能初始化全部迁移。
- ArchUnit 能阻止模块访问其它模块的 Mapper 和 Entity。

### M1

- 可以创建租户、集团、两个法人公司和多级组织。
- 同一人员可以具有跨公司、多岗位和有效期任职。
- 组织移动、停用和历史任职有一致规则。
- 旧 IAM 组织数据可以通过迁移脚本升级。

### M2

- 租户 A 无法通过 ID、查询参数、请求体或导出访问租户 B 数据。
- 密码不再使用无盐 SHA-256。
- 所有受保护 API 通过统一安全链路授权。
- 角色绑定和数据权限覆盖公司、组织、任职和本人范围。
- 平台跨租户操作具有权限、原因和审计记录。

### M3

- 至少接入两个模型供应商或一个供应商加一个本地兼容端点。
- AI 请求具备租户限额、费用、延迟和错误记录。
- 知识检索按用户权限过滤，并返回来源引用。
- 默认向量存储适配器通过租户命名空间隔离测试。
- 至少完成一个 MCP 工具和一个平台内部工具的注册与调用。
- Agent 工具调用经过 API 权限和数据权限检查。
- 高风险写工具需要人工确认。

### M4

- 第三方开发者可以用模板创建模块。
- 生成结果包含迁移、后端、前端、权限和测试。
- 示例模块能够 clean build、启动并通过端到端测试。
- 模块不访问其它模块内部实现。

### M5

- 新开发者按 README 可以在 30 分钟内启动项目。
- 核心安全与租户隔离测试全部自动化。
- 提供从当前版本升级到 v0.1 的迁移指南。
- 发布包不包含默认生产密码和明文凭证。
- 文档、示例、版本和数据库迁移保持一致。

## 14. Definition of Done

任何功能只有同时满足以下条件才算完成：

- 领域规则和边界已经明确。
- API、权限码、错误码和审计行为已经定义。
- 租户隔离和数据权限经过负向测试。
- 数据库迁移可以从空库和上一版本升级。
- 后端单元或集成测试覆盖关键行为。
- 前端包含加载、成功、空数据、无权限和失败状态。
- 文档和示例已更新。
- clean build、静态检查、测试和安全扫描通过。
- AI 功能额外记录模型、Prompt、知识、工具、Token 和费用信息。
